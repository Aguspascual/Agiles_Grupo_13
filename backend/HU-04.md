# HU-04: alta y consulta de horarios recurrentes

Entrega intermedia de los contratos v1 aprobados de TDD-0001 y TDD-0004:
alta de un día y consulta semanal/individual por cancha. Modificación y baja
(TDD-0002 y TDD-0003) siguen pendientes para la siguiente unidad aprobada.
No incluye reservas, generación de turnos, bloqueos por fecha ni frontend.

## Ejecutar

Preparar las bases y variables con [PostgreSQL local](LOCAL.md). Desde `backend/`:

```powershell
. ./scripts/local-env.ps1
go run ./cmd/api
```

La API aplica las migraciones embebidas 001–004 una sola vez por base. Ejecutar
una sola instancia mientras migra: el runner existente no coordina arranques
concurrentes. No borrar ni editar migraciones previas ni usar credenciales de
desarrollo en producción.

## Contrato HTTP implementado

Base: `/api/v1/complexes/{complexId}/courts/{courtId}/weekly-schedule/days`.
IDs UUID; `weekday` de 1 (lunes) a 7 (domingo). Requiere JWT Bearer válido,
complejo/cancha activos y ADMIN o encargado asignado al complejo.

| Operación | Método y ruta relativa | Resultado |
| --- | --- | --- |
| Alta de día ausente | `POST /` sin barra final | `201`, `Location` al día y `ETag` |
| Semana | `GET /` sin barra final | `200 {"days":[...]}`, orden lunes–domingo |
| Día | `GET /{weekday}` | `200 {"day":...}`, `ETag`; ausente `404` |

Los cuerpos JSON son estrictos: campos mostrados obligatorios, tipos correctos,
sin propiedades desconocidas, revisión ni IDs de franjas enviados por el cliente.
Las consultas no admiten parámetros adicionales ni cuerpo. Las respuestas de
horarios usan `Cache-Control: no-store`. HEAD conserva la respuesta vacía después
de validar ruta y rol, sin consultar horarios.

POST:

```json
{"weekday":1,"enabled":true,"durationMinutes":60,"intervals":[{"opensAt":"09:00","closesAt":"13:00"},{"opensAt":"17:00","closesAt":"20:00"}]}
```

Respuesta:

```json
{"day":{"weekday":1,"enabled":true,"durationMinutes":60,"revision":"9ad461f4-86b5-459b-854c-1ddf15d9b033","intervals":[{"id":"0df09989-542c-49f9-8fe4-c3596827bce9","opensAt":"09:00","closesAt":"13:00"},{"id":"1ee3db40-5e43-4af5-8a49-f61a6e2fb369","opensAt":"17:00","closesAt":"20:00"}]}}
```

Un día habilitado requiere franjas; uno deshabilitado admite un arreglo vacío,
no `null`. Duraciones 60/90; cada franja admite al menos un turno completo, sin
exigir divisibilidad exacta. Horas `HH:mm` de `00:00` a `23:59`, cierre posterior
a apertura, sin cruce de medianoche. Se permiten franjas contiguas, no superpuestas.
Son horas locales, sin conversión a UTC: `America/Argentina/Buenos_Aires`.

Ejemplo PowerShell, con IDs y JWT del flujo de autenticación/complejos/canchas:

```powershell
$headers = @{ Authorization = "Bearer $token" }
$base = "http://localhost:8000/api/v1/complexes/$complexId/courts/$courtId/weekly-schedule/days"
$body = '{"weekday":1,"enabled":true,"durationMinutes":60,"intervals":[{"opensAt":"09:00","closesAt":"13:00"}]}'
Invoke-WebRequest -UseBasicParsing $base -Method Post -Headers $headers -ContentType application/json -Body $body
Invoke-RestMethod "$base/1" -Headers $headers
```

La semana sin configuración devuelve `{"days":[]}`, sin días o valores inventados.
Formato de errores `{"error":"mensaje"}`, sin detalles SQL ni secretos:
`400` entrada inválida, `401` autenticación inválida, `403` sin permiso,
`404` recurso ausente/inactivo, `409` día duplicado, `500` error interno.

## Persistencia y organización

`internal/schedules/` contiene modelo, validación, handlers `list`, `get`, `create`
y repositorio PostgreSQL. `cmd/api/routes.go` compone las tres rutas de horarios;
`migrations/004_weekly_schedules.sql` agrega cabeceras y franjas.

El módulo reutiliza UUID y JSON estricto de `auth`, con límite de cuerpo de 64 KiB.
`complexes.AuthorizeInTransaction` comprueba el complejo activo dentro de la
transacción; se conserva su bloqueo compartido y el bloqueo de cancha. El alta
bloquea la cancha y persiste cabecera y franjas atómicamente. La unicidad evita
sobrescribir días existentes bajo concurrencia. La consulta reúne cabecera y
franjas en una sentencia, ordenadas por día y hora.

## Fases y validación de esta unidad

Las fases Red observadas durante la implementación original incluyeron validaciones
que aceptaban entradas inválidas, rutas ausentes, tablas faltantes y persistencia
no implementada. Esta separación en commits conserva las pruebas del alta y la
consulta; no presenta una fase Red retrospectiva nueva.

Pruebas principales: `internal/schedules/*_test.go` y `cmd/api/routes_test.go`.

```powershell
. ./scripts/local-env.ps1
go test -count=1 ./...
go vet ./...
go test -count=1 -v ./cmd/api -run TestHTTPPostgresHU04Flow
```

El flujo HTTP usa TCP y PostgreSQL reales: registro/login, complejo, cancha,
semana vacía, permisos, alta, consulta y persistencia tras reiniciar HTTP. Las
pruebas SQL verifican migración, permisos, otra conexión, día duplicado, alta
concurrente única y rollback. Cada prueba usa un esquema temporal de
`padelmatch_test`, nunca desarrollo. Sin `TEST_DATABASE_URL` o con `-short`, las
integraciones se omiten y no cuentan como aprobadas.

## Límites y siguiente unidad

PUT y DELETE de horarios aún no se exponen. Se mantienen sus contratos aprobados
sin modificarlos; la siguiente unidad implementará modificaciones y bajas con
protección de revisión y rechazo explícito cuando falte la fuente de reservas.
La base actual no tiene reservas reales: no se usa ningún checker ficticio que
simule su ausencia ni se afirma verificada esa integración. La futura creación
de reservas debe coordinar transaccionalmente el bloqueo de cancha.

La HU completa, generación de próximas semanas, bloqueos puntuales,
reprogramación y conexión frontend siguen pendientes y fuera de esta unidad.
