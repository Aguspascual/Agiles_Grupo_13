## Contrato HTTP

Base: `/api/v1/complexes/{complexId}/courts/{courtId}/weekly-schedule/days`.
Los IDs son UUID; `weekday` va de 1 (lunes) a 7 (domingo). Requiere JWT Bearer
válido, complejo/cancha activos y ADMIN o encargado asignado al complejo.

| Operación | Método y ruta relativa | Resultado |
| --- | --- | --- |
| Alta de día ausente | `POST /` sin barra final | `201`, `Location` al día y `ETag` |
| Semana | `GET /` sin barra final | `200 {"days":[...]}`, orden lunes–domingo |
| Día | `GET /{weekday}` | `200 {"day":...}`, `ETag`; ausente `404` |
| Modificación completa | `PUT /{weekday}` | `200 {"day":...}`, nueva revisión |
| Baja | `DELETE /{weekday}` | Contrato `204`; actualmente `503` por dependencia ausente |

Los cuerpos JSON son estrictos: campos mostrados obligatorios, tipos correctos,
sin propiedades desconocidas, revisión ni IDs de franjas enviados por el cliente.
PUT no recibe `weekday` y nunca crea un día ausente. Las consultas no admiten
parámetros adicionales ni cuerpo; DELETE tampoco admite cuerpo.
Las respuestas de horarios usan `Cache-Control: no-store`.

POST:

```json
{"weekday":1,"enabled":true,"durationMinutes":60,"intervals":[{"opensAt":"09:00","closesAt":"13:00"},{"opensAt":"17:00","closesAt":"20:00"}]}
```

Respuesta:

```json
{"day":{"weekday":1,"enabled":true,"durationMinutes":60,"revision":"9ad461f4-86b5-459b-854c-1ddf15d9b033","intervals":[{"id":"0df09989-542c-49f9-8fe4-c3596827bce9","opensAt":"09:00","closesAt":"13:00"},{"id":"1ee3db40-5e43-4af5-8a49-f61a6e2fb369","opensAt":"17:00","closesAt":"20:00"}]}}
```

Un día habilitado requiere franjas; uno deshabilitado puede tener un arreglo vacío,
no `null`. Cada franja admite al menos un turno completo, sin exigir divisibilidad
exacta. Duraciones 60/90, horas `HH:mm` de `00:00` a `23:59`, cierre posterior a
apertura, sin cruce de medianoche. Se permiten franjas contiguas, no superpuestas.
Las horas recurrentes son locales; no se convierten a UTC. Referencia temporal:
`America/Argentina/Buenos_Aires`.

## Modificar sin perder cambios ajenos

PUT y DELETE requieren el `ETag` de la última lectura:

```http
If-Match: "9ad461f4-86b5-459b-854c-1ddf15d9b033"
```

El cuerpo completo de PUT para deshabilitar y cambiar la duración conserva franjas:

```json
{"enabled":false,"durationMinutes":90,"intervals":[{"opensAt":"09:00","closesAt":"13:00"},{"opensAt":"17:00","closesAt":"20:00"}]}
```

Reactivar usa `true`. Estos cambios mantienen los IDs de franjas y no alteran
reservas. Cada modificación exitosa rota la revisión, incluso un reenvío idéntico.
Tras `412`, volver a consultar y revisar el cambio; no sobrescribir automáticamente.

Ejemplo PowerShell, con IDs y JWT obtenidos del flujo de autenticación/complejos/canchas:

```powershell
$headers = @{ Authorization = "Bearer $token" }
$base = "http://localhost:8000/api/v1/complexes/$complexId/courts/$courtId/weekly-schedule/days"
$body = '{"weekday":1,"enabled":true,"durationMinutes":60,"intervals":[{"opensAt":"09:00","closesAt":"13:00"}]}'
$created = Invoke-WebRequest -UseBasicParsing $base -Method Post -Headers $headers -ContentType application/json -Body $body
$headers['If-Match'] = $created.Headers['ETag']
$body = '{"enabled":false,"durationMinutes":90,"intervals":[{"opensAt":"09:00","closesAt":"13:00"}]}'
$updated = Invoke-WebRequest -UseBasicParsing "$base/1" -Method Put -Headers $headers -ContentType application/json -Body $body
Invoke-RestMethod "$base/1" -Headers @{ Authorization = "Bearer $token" }
```

La semana sin configuración devuelve `{"days":[]}`, sin inventar días o valores
por defecto. El almacenamiento de demostración del frontend no se migra ni conecta.

## Errores y protección de reservas

Formato `{"error":"mensaje"}`, sin detalles de SQL ni secretos:
`400` entrada inválida, `401` autenticación inválida, `403` sin permiso,
`404` recurso ausente/inactivo, `409` duplicado o conflicto de reservas,
`412` revisión vieja, `428` falta If-Match, `500` error interno.

La base actual **no tiene una fuente de reservas reales**. Por eso:
- Todo DELETE y PUT que cambie el conjunto de franjas responde `503`, sin cambios,
  incluso si se sospecha que no hay reservas. No se sustituye ese control por un fake.
- PUT con franjas equivalentes (comparadas ordenadas por hora), modificando solo
  habilitación/duración, se permite: no cancela, mueve ni recalcula reservas.
- El camino transaccional de baja/reemplazo está preparado detrás de
  `FutureReservationChecker`, pero su éxito y conflictos con reservas reales
  **no están verificados**. El constructor de producción instala indisponibilidad explícita.

Las escrituras bloquean la fila de cancha, como la baja de canchas existente.
La futura confirmación de reservas debe tomar ese mismo bloqueo y comprobar
horarios, estado y ocupación real dentro de su transacción. Una consulta previa,
un mock o una grilla calculada no garantizan exclusión. No habilitar esas
operaciones con un checker que siempre devuelva `false`.

## Organización y helpers compartidos

Los handlers de horarios están separados por operación (`list`, `get`, `create`,
`update`, `delete`), siguiendo el patrón de canchas. Reutilizan la validación UUID
y el decodificador JSON estricto de `auth`; cada módulo conserva su límite de
cuerpo y sus mensajes: autenticación/complejos 1 MiB, canchas 7 MiB, horarios 64 KiB.
La pertenencia al complejo activo se comprueba mediante
`complexes.AuthorizeInTransaction` dentro de la transacción del repositorio,
sin perder el bloqueo compartido del complejo ni el bloqueo de cancha.

temporal dentro de `padelmatch_test`; nunca desarrollo. Sin `TEST_DATABASE_URL`
o con `-short`, las nuevas integraciones se omiten y no cuentan como aprobadas.
